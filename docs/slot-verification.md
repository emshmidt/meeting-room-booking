# Проверка создания и поиска слотов

**Дата проверки:** 12 ноября 2026 года.

## Реализованное поведение

- `POST /api/v1/rooms/{roomId}/slots` создаёт слот существующей комнаты; операция разрешена ADMIN.
- CreateSlotRequest принимает startsAt/endsAt как OffsetDateTime, roomId передаётся в пути. Модель и ответ используют Instant; время ответа сериализуется в UTC с Z.
- До сохранения проверяются обязательность времён, начало в целый час UTC и длительность ровно 60 минут. Создание слота в прошлом не запрещено; доступность определяется отдельно.
- Уникальность проверяется по паре `(roomId, startsAt)` после нормализации времени. Метод SlotService.createSlot синхронизирован: проверка дубликата и сохранение выполняются под одним монитором сервиса. Это гарантия в одном процессе; отдельного конкурентного теста нет.
- Сервис создаёт UUID и сохраняет TimeSlot; ответ 201 содержит id, roomId, startsAt, endsAt и available.
- `GET /api/v1/rooms/{roomId}/slots` отбирает слоты комнаты по началу внутри `[from, to)`. from/to обязательны и должны удовлетворять from < to.
- available=true означает строго будущее начало и отсутствие ACTIVE-брони слота. CANCELLED не занимает слот. availableOnly=false по умолчанию; при true недоступные слоты исключаются.
- Для одного GET используются один now из Clock и один снимок броней; те же данные применяются для фильтра и флагов ответа. Чтение не резервирует слот.
- totalElements считается после фильтров, до страницы. Порядок: startsAt ASC, id ASC; page=0 и size=20 по умолчанию. Контроллер проверяет page >= 0 и size в диапазоне 1–100; смещение вычисляется в long.
- Предметные исключения раздельно переводятся в 400/403/404/409. В getPage существование комнаты проверяется до проверки периода.

## Объём подтверждения

- HTTP подтверждает успешное создание, нормализацию эквивалентного времени при проверке дубликата, отбор по периоду, вычисление доступности на исходных данных, пагинацию, неверную длительность/выравнивание/период, конфликты и запрет создания для USER.
- GET после конфликта Orion подтверждает отсутствие дополнительного слота в проверенном диапазоне.
- Запрос неизвестной комнаты одновременно содержит неверный период. Его 404 подтверждает порядок проверок, но не является изолированной HTTP-проверкой отсутствия комнаты с корректным периодом.
- После неверных POST Luna и после запрещённого POST Anna отдельные GET состояния не зафиксированы. По исходникам эти отказы происходят до save.
- Пустая страница, страница за концом, большое смещение, неверные page/size, отсутствие/формат времён, точная граница now и параллельное создание слотов отдельно по HTTP здесь не подтверждены. Соответствующие реализованные ветви изучены по исходникам в пределах доступного кода.

## Связь с SQL

В `sql/09-day-3-subqueries.sql` отсутствие ACTIVE проверяется через NOT EXISTS по совпадающему slot_id. В SlotService этому соответствует фильтр броней данного слота с последующим noneMatch по ACTIVE. Для полной доступности дополнительно требуется startsAt > now; сам SQL-пример проверяет только отсутствие ACTIVE.

SQL при этой проверке повторно не запускался. Приложение использует in-memory репозитории и не обращается к PostgreSQL.

## Воспроизведение

1. Из корня проекта выполнить `./mvnw package` и запустить актуальный JAR с `--app.demo-user=vera`.
2. Выполнить запросы HTTP-файла от ADMIN по порядку. Для воспроизведения дубликата с другим смещением сохранить один процесс между созданием Luna и повторным POST.
3. Выполнить помеченные дополнительные проверки при необходимости; их ожидаемые результаты отделены от зафиксированных.
4. Остановить процесс Vera, запустить с `--app.demo-user=anna` и выполнить проверку запрета и контроль состояния Luna.

Каждый перезапуск восстанавливает исходное наполнение: 4 комнаты, 3 пользователя, 8 слотов, 6 броней. Созданные слоты и их UUID не переносятся. Исходные UUID Orion и Luna стабильны. Для времён со смещением в query string знак `+` кодируется как `%2B` либо используется curl --get --data-urlencode; JSON такого кодирования не требует.

## Текущие ограничения

- Данные хранятся в памяти одного процесса. PostgreSQL, транзакции БД и защита нескольких экземпляров приложения не подключены.
- Пользователь выбирается серверной настройкой app.demo-user. Аутентификация HTTP-клиента отсутствует.
- Предметные ошибки слотов возвращаются без тела; единый формат code/message/fieldErrors не реализован. Ошибки преобразования параметров и проверки page/size используют стандартную обработку Spring.
- Полная строгая обработка JSON и query parameters, включая проверку ограниченного набора строк для availableOnly, не реализована.
- Четыре операции комнат и слотов реализованы. HTTP-операции бронирования отсутствуют.

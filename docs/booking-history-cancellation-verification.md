## Условия воспроизведения

- Backend запускается из корня `booking-training`, базовый адрес `http://localhost:8080`.
- Исходный Java seed содержит 4 комнаты, 3 пользователя, 8 слотов и 6 броней. На старте Anna имеет 3 брони, Boris — 3, Vera — 0.
- Текущий пользователь определяется серверной настройкой `--app.demo-user=anna`, `boris` или `vera`. При смене роли процесс перезапускается и память восстанавливается из seed.
- Времена таблиц приведены по Москве, UTC+3. Исходные заголовки `Date` используют GMT. Поля JSON сохранены в UTC.
- Сценарии истории и отмены находятся в [bookings.http](../requests/bookings.http). UUID двух созданных броней при повторении берутся из новых ответов POST.

## Сверка реализации и дальнейшие проверки

По исходникам `getPage` получает один снимок, фильтрует владельца и статус, считает общий размер до страницы, сортирует `createdAt DESC, id DESC` и вычисляет смещение в `long`. `toBookingResponse` используется повторно. Отсутствующий связанный слот приводит к `BookingSlotMissingException`.

`updateStatus` синхронизирован, проверяет аргументы и существование записи, сохраняет все поля, кроме статуса. `createBooking` и `cancelBooking` синхронизированы на одном экземпляре сервиса. При отмене доступ проверяется перед статусом, а время проверяется после раннего успешного завершения для отменённой записи. Контроллер сопоставляет `CancellationClosedException` с HTTP 409.

В этом прогоне ошибки параметров приходили в стандартном JSON Spring, а проверенные предметные ошибки возвращали пустое тело. Единый формат `code`, `message`, `fieldErrors`, строгая обработка пустых query-параметров и проверка типов JSON требуют отдельных проверок.

Отдельная проверка конкурентного бронирования запланирована.

В SQL своя история соответствует `WHERE user_id = …` и `ORDER BY created_at DESC, id DESC`, отмена соответствует `UPDATE status`. Запись CANCELLED выходит из частичного индекса ACTIVE, освобождая возможность новой брони. Результаты SQL-проверок приведены в [заметках о транзакциях](transactions.md).

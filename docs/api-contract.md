# Контракт API сервиса бронирования переговорных

Сервис позволяет пользователям находить свободные часовые слоты переговорных, создавать брони, просматривать свою историю и отменять бронирования с сохранением записей. Администраторы создают комнаты и слоты, а также могут просматривать и отменять чужие брони по правилам доступа.

Документ описывает планируемое поведение API первой версии.

## Операции API

### GET /api/v1/rooms

**Назначение:** Получить список комнат с фильтром вместимости и пагинацией.

**Вход:** Query parameters: `minCapacity` — необязательный; `page` — по умолчанию 0; `size` — по умолчанию 20. Тела запроса нет.

**Выход:** Страница комнат: `items`, `page`, `size`, `totalElements`. Каждый элемент `items` содержит `id`, `name`, `capacity`, `hasProjector`, `description`.

**Успешный статус:** `200 OK`, в том числе при пустом списке.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован; `500 Internal Server Error` — внутренний сбой.

**Доступ:** Аутентифицированный пользователь с ролью USER или ADMIN.

### POST /api/v1/rooms

**Назначение:** Добавить новую комнату

**Вход:** Тело запроса: `name` - обязательный; `capacity` - обязательный; 
`hasProjector` - обязательный; `description` - необязательный.

**Выход:** Данные о комнате: `id`, `name`, `capacity`, `hasProjector`, `description`.

**Успешный статус:** `201 Created`.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован; 
`500 Internal Server Error` — внутренний сбой; `403 Forbidden` — операция запрещена установленному пользователю.

**Доступ:** Аутентифицированный пользователь с ролью ADMIN.

### GET /api/v1/rooms/{roomId}/slots

**Назначение:** Получить список слотов комнаты с фильтром по периоду и активности и пагинацией.

**Вход:**

- Параметр пути: `roomId` — обязательный UUID комнаты, слоты которой запрашиваются.
- Query parameters: `from` — обязательный; `to` — обязательный; `availableOnly` — необязательный; `page` — по умолчанию 0; `size` — по умолчанию 20.
- Тело запроса отсутствует.

**Выход:** Страница слотов: `items`, `page`, `size`, `totalElements`. 
Каждый элемент `items` содержит `id`, `roomId`, `startsAt`, `endsAt`, `available`.

**Успешный статус:** `200 OK`, в том числе при пустом списке.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`404 Not Found` — комната не найдена; `500 Internal Server Error` — внутренний сбой.

**Доступ:** Аутентифицированный пользователь с ролью USER или ADMIN.

### POST /api/v1/rooms/{roomId}/slots

**Назначение:** Добавление слота по комнате.

**Вход:**

- Параметр пути: `roomId` — обязательный UUID комнаты, для которой создаётся слот.
- JSON-тело: `startsAt` — обязательный; `endsAt` — обязательный.

**Выход:** Данные о слоте: `id`, `roomId`,`startsAt`, `endsAt`, `available`.

**Успешный статус:** `201 Created`.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`404 Not Found` — комната не найдена; `500 Internal Server Error` — внутренний сбой;
`403 Forbidden` — операция запрещена установленному пользователю; `409 Conflict` — слот этой комнаты с таким началом уже существует.

**Доступ:** Аутентифицированный пользователь с ролью ADMIN.

### POST /api/v1/bookings

**Назначение:** Добавить бронирование.

**Вход:** Тело: `slotId` - обязательный.

**Выход:** Данные о бронировании: `id`, `userId`, `slotId`, `status`, `createdAt`,
`roomId`, `startsAt`, `endsAt`.
Location: /api/v1/bookings/{id}

**Успешный статус:** `201 Created`.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`409 Conflict` — слот занят или уже начался; `500 Internal Server Error` — внутренний сбой;
`404 Not Found` — слот не найден.

**Доступ:** Аутентифицированный пользователь с ролью USER или ADMIN.

### GET /api/v1/bookings

**Назначение:** История текущего пользователя, включая отменённые брони.

**Вход:** Query parameters: `status` — необязательный; `page` — по умолчанию 0; `size` — по умолчанию 20. Тела запроса нет.

**Выход:** Страница бронирований: `items`, `page`, `size`, `totalElements`.
Каждый элемент `items` содержит `id`, `userId`, `slotId`, `status`, `createdAt`,
`roomId`, `startsAt`, `endsAt`.

**Успешный статус:** `200 OK`, в том числе при пустом списке.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`403 Forbidden` — операция запрещена установленному пользователю; `500 Internal Server Error` — внутренний сбой.

**Доступ:** Аутентифицированный пользователь USER или ADMIN.

### GET /api/v1/bookings/{id}

**Назначение:** Получить бронирование по id.

**Вход:** Параметр пути есть, query parameters и тела нет.

**Выход:** Данные о бронировании: `id`, `userId`, `slotId`, `status`, `createdAt`,
`roomId`, `startsAt`, `endsAt`.

**Успешный статус:** `200 OK`.

**Ошибки:** `400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`403 Forbidden` — операция запрещена установленному пользователю; `500 Internal Server Error` — внутренний сбой;
`404 Not Found` — бронирование не найдено.

**Доступ:** Аутентифицированный пользователь владелец или с ролью ADMIN.

### DELETE /api/v1/bookings/{id}

**Назначение:** Отменить бронирование.

**Вход:** Параметр пути есть, query parameters и тела нет.

**Выход:** Тело ответа отсутствует.

**Успешный статус:** `204 No Content`.

**Ошибки:**`400 Bad Request` — неверные параметры; `401 Unauthorized` — пользователь не аутентифицирован;
`403 Forbidden` — операция запрещена установленному пользователю; `500 Internal Server Error` — внутренний сбой;
`409 Conflict` — активное бронирование уже нельзя отменить по времени; `404 Not Found` — бронирование не найдено.

**Доступ:** Аутентифицированный пользователь владелец или с ролью ADMIN.


# Форматы данных

В таблицах указываются типы JSON. Для запроса обязательность означает, что клиент должен передать поле; для ответа — что сервер всегда включает его в представление. Возможность значения `null` описывается отдельно.

UUID передаются строками в стандартном формате с дефисами. Время передаётся строкой даты и времени с явным смещением (например, 2030-01-14T12:00:00+03:00). В ответах сервер приводит время к UTC и использует суффикс Z (тот же момент: 2030-01-14T09:00:00Z).

## CreateRoomRequest

**Назначение:** JSON-тело запроса POST /api/v1/rooms для создания комнаты.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `name` | string | Да | Нет | Пробелы по краям удаляются; оставшаяся строка непустая | Клиент |
| `capacity` | number, целое | Да | Нет | Целое число больше 0; строка с цифрами не подходит | Клиент |
| `hasProjector` | boolean | Да | Нет | true или false; false является полноценным значением | Клиент |
| `description` | string или null | Нет | Да | Можно пропустить или передать null; пустая строка допустима; отсутствие сохраняется как NULL | Клиент |

Идентификатор комнаты создаёт сервер; он возвращается в RoomResponse. Ошибки типов, обязательности и правил полей возвращаются как 400 Bad Request.

## RoomResponse

**Назначение:** Представление комнаты в ответе создания и в элементах страницы комнат.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `id` | string (UUID) | Да | Нет | Идентификатор существующей комнаты | Сервер; сохранён в rooms.id |
| `name` | string | Да | Нет | Название комнаты; после удаления пробелов по краям непустое | Сервер из rooms.name |
| `capacity` | number, целое | Да | Нет | Целое число больше 0 | Сервер из rooms.capacity |
| `hasProjector` | boolean | Да | Нет | true или false — наличие проектора | Сервер из rooms.has_projector |
| `description` | string или null | Да | Да | Поле включается всегда; при отсутствии описания null; пустая строка сохраняется | Сервер из rooms.description |

## CreateSlotRequest

**Назначение:** JSON-тело запроса создания слота. Обязательный UUID комнаты roomId берётся из пути.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `startsAt` | string (дата-время) | Да | Нет | Явное смещение; момент после приведения к UTC приходится на целый час: минуты, секунды и доли секунды равны 0 | Клиент |
| `endsAt` | string (дата-время) | Да | Нет | Явное смещение; момент ровно на 60 минут позже startsAt | Клиент |

Правила для сочетания полей: длительность 60 минут и уникальность комнаты с моментом начала. Комната должна существовать; roomId в JSON-теле не передаётся.

## SlotResponse

**Назначение:** Представление слота в ответе создания и в элементах страницы слотов.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `id` | string (UUID) | Да | Нет | Идентификатор слота | Сервер; сохранён в time_slots.id |
| `roomId` | string (UUID) | Да | Нет | Идентификатор комнаты, которой принадлежит слот | Сервер из time_slots.room_id; при создании берётся из пути |
| `startsAt` | string (дата-время) | Да | Нет | UTC с суффиксом Z; начало в целый час UTC; может быть в прошлом при чтении истории слотов | Сервер из time_slots.starts_at |
| `endsAt` | string (дата-время) | Да | Нет | UTC с суффиксом Z; ровно на 60 минут позже startsAt | Сервер из time_slots.ends_at |
| `available` | boolean | Да | Нет | true, если startsAt строго позже текущего времени и нет ACTIVE-брони; иначе false; состояние на момент проверки, без резервирования | Сервер вычисляет по времени и bookings; отдельного столбца нет |

## CreateBookingRequest

**Назначение:** JSON-тело запроса POST /api/v1/bookings для создания брони.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `slotId` | string (UUID) | Да | Нет | Корректный формат UUID; пустая строка и неверный формат отклоняются с 400 | Клиент |

Проверки сценария: слот существует, его начало ещё не наступило, активной брони нет. Неизвестный слот даёт 404, занятость или наступившее начало — 409. userId, id, status и createdAt задаются сервером и не входят в запрос.

## BookingResponse

**Назначение:** Представление брони в ответах создания, получения одной брони и в элементах страницы истории.

| Поле | Тип JSON | Поле обязательно? | Допускает null? | Правила | Источник значения |
|---|---|---|---|---|---|
| `id` | string (UUID) | Да | Нет | Идентификатор брони; при создании совпадает с идентификатором в Location | Сервер; сохранён в bookings.id |
| `userId` | string (UUID) | Да | Нет | Идентификатор владельца брони; при создании определяется по текущему пользователю | Сервер из bookings.user_id; личность установлена сервером |
| `slotId` | string (UUID) | Да | Нет | Идентификатор забронированного слота | Сервер из bookings.slot_id; при создании из проверенного запроса |
| `roomId` | string (UUID) | Да | Нет | Идентификатор комнаты связанного слота | Сервер через bookings.slot_id → time_slots.room_id |
| `status` | string | Да | Нет | ACTIVE или CANCELLED; новая бронь получает ACTIVE; отменённая запись сохраняется | Сервер из bookings.status |
| `startsAt` | string (дата-время) | Да | Нет | UTC с суффиксом Z; время начала слота, может быть в прошлом в истории | Сервер из time_slots.starts_at через слот брони |
| `endsAt` | string (дата-время) | Да | Нет | UTC с суффиксом Z; ровно на 60 минут позже startsAt | Сервер из time_slots.ends_at через слот брони |
| `createdAt` | string (дата-время) | Да | Нет | UTC с суффиксом Z; время создания записи брони; при отмене не меняется | БД фиксирует при вставке; сервер читает bookings.created_at |

## Параметры коллекций

Все перечисленные параметры передаются в query string. Их значения разбираются как указанные типы. Пагинация применяется после отбора данных и сортировки.

### Общая пагинация

Применяется к GET /api/v1/rooms, GET /api/v1/rooms/{roomId}/slots и GET /api/v1/bookings.

| Параметр | Тип значения | Обязательный? | По умолчанию | Допустимые значения |
|---|---|---|---|---|
| `page` | Целое число | Нет | 0 | Целое число не меньше 0; нумерация страниц начинается с нуля |
| `size` | Целое число | Нет | 20 | Целое число от 1 до 100 включительно |

Если параметр отсутствует, используется значение по умолчанию. Неверный тип, отрицательный page, size меньше 1 или больше 100 возвращают 400 Bad Request. Значения автоматически не округляются и не ограничиваются допустимой границей.

Страница выбирается с пропуском page × size подходящих записей и возвращает не больше size элементов. Например, page=2 и size=10 означают третью страницу: пропускаются 20 записей, выбираются следующие, максимум 10.

### Комнаты — GET /api/v1/rooms

| Параметр | Тип значения | Обязательный? | По умолчанию | Правило |
|---|---|---|---|---|
| `minCapacity` | Целое число | Нет | Фильтр отсутствует | Больше 0; выбираются комнаты с capacity не меньше minCapacity |
| `page` | Целое число | Нет | 0 | Общие правила пагинации |
| `size` | Целое число | Нет | 20 | Общие правила пагинации |

**Сортировка:** capacity по возрастанию, затем id по возрастанию. При одинаковой вместимости id задаёт однозначный порядок. Неверный minCapacity возвращает 400 Bad Request.

### Слоты комнаты — GET /api/v1/rooms/{roomId}/slots

Обязательный roomId передаётся в пути и выбирает комнату. Параметры ниже уточняют отбор её слотов.

| Параметр | Тип значения | Обязательный? | По умолчанию | Правило |
|---|---|---|---|---|
| `from` | Дата-время с явным смещением | Да | Нет | Включительная нижняя граница времени начала слота |
| `to` | Дата-время с явным смещением | Да | Нет | Исключительная верхняя граница времени начала слота; момент строго позже from |
| `availableOnly` | Boolean | Нет | false | true — только доступные слоты; false — все слоты комнаты в указанном периоде |
| `page` | Целое число | Нет | 0 | Общие правила пагинации |
| `size` | Целое число | Нет | 20 | Общие правила пагинации |

Период определяется как [from, to): отбирается начало слота, а не любое пересечение интервалов. Например, для периода с 09:00Z до 11:00Z на одну дату слоты с началом в 09:00Z и 10:00Z включаются, с началом в 11:00Z — нет. Границы сравниваются как моменты времени с учётом переданного смещения.

При availableOnly=true нужны одновременно два условия: startsAt строго позже текущего времени и отсутствие брони ACTIVE для слота. При false дополнительного отбора по доступности нет. Поле available рассчитывается для каждого возвращаемого слота по тем же двум условиям; прошедший свободный слот имеет available=false.

**Сортировка:** startsAt по возрастанию, затем id по возрастанию.

Отсутствующие from/to, неверный формат времени, отсутствие смещения, from не раньше to или значение availableOnly, отличное от true/false, возвращают 400 Bad Request. Если существующая комната не имеет подходящих слотов, возвращается 200 OK с пустым items; если комнаты нет — 404 Not Found.

Доступность отражает состояние на момент проверки и не резервирует слот. Успешное чтение доступного слота не гарантирует успех последующего создания брони.

### Свои брони — GET /api/v1/bookings

Коллекция всегда ограничена текущим пользователем, включая обращения ADMIN. Произвольный userId для выбора чужой истории этим endpoint не поддерживается.

| Параметр | Тип значения | Обязательный? | По умолчанию | Правило |
|---|---|---|---|---|
| `status` | Строка | Нет | Фильтр отсутствует | ACTIVE или CANCELLED; при отсутствии возвращаются оба статуса |
| `page` | Целое число | Нет | 0 | Общие правила пагинации |
| `size` | Целое число | Нет | 20 | Общие правила пагинации |

**Сортировка:** createdAt по убыванию, затем id по убыванию. Неизвестный status возвращает 400 Bad Request. Отменённые брони сохраняются и входят в историю, если не исключены фильтром.

Порядок всех трёх коллекций фиксирован; произвольный параметр sort первой версией не поддерживается. Дополнительный id разрешает равенство основного поля, но не означает хронологию. Однозначный порядок не исключает сдвиг страниц при изменении данных между запросами.

## Формат страницы

Все четыре поля присутствуют в каждом успешном ответе коллекции и не равны null.

| Поле | Тип JSON | Значение и правила |
|---|---|---|
| `items` | array | Элементы текущей страницы; для комнат — RoomResponse, для слотов — SlotResponse, для истории — BookingResponse. Может быть пустым массивом; количество элементов не больше size |
| `page` | number, целое | Запрошенный номер страницы, начиная с 0; при отсутствии параметра — 0 |
| `size` | number, целое | Применённый максимальный размер страницы, 1–100; при отсутствии параметра — 20. Не равен обязательно количеству элементов items |
| `totalElements` | number, целое | Общее количество подходящих записей после всех фильтров, включая комнату/период или текущего пользователя, но до ограничения страницы; не меньше 0 |

Если подходящих записей нет или запрошенная страница находится за концом списка, возвращается 200 OK с items=[]. page и size сохраняют запрошенные либо принятые по умолчанию значения; totalElements отражает количество всех подходящих записей, а не только текущей страницы.

Пример расчёта на условном наборе из 43 подходящих записей: при page=4 и size=10 items содержит 3 записи (позиции 41–43), totalElements=43. При page=5 на том же наборе items пуст, но totalElements по-прежнему равен 43.

# Ошибки, доступ и повторная отмена

Этот раздел уточняет планируемое поведение всех операций первой версии. Статусы, коды причин и правила доступа применяются совместно с описаниями endpoint выше.

## Единый формат ошибки

HTTP-статус передаётся как статус ответа, а тело ошибки имеет Content-Type: application/json. Тело содержит следующие поля:

| Поле | Тип JSON | Обязательное? | Смысл |
|---|---|---|---|
| `code` | string | Да | Стабильный код конкретной причины ошибки; клиент использует его для обработки ситуации |
| `message` | string | Да | Понятное человеку описание ошибки; текст может уточняться без изменения code |
| `fieldErrors` | array | Да | Ошибки отдельных полей тела, параметров пути или query parameters; при отсутствии ошибок конкретных полей — пустой массив |

Все три поля не равны null. Каждый элемент fieldErrors — объект с обязательными строковыми полями field и message: field обозначает имя проблемного поля/параметра (например, slotId, roomId, page или startsAt), message объясняет нарушение.

Для сломанного JSON используется MALFORMED_JSON с пустым fieldErrors: запрос нельзя корректно разобрать. Для корректного JSON с неверным UUID, типом или обязательным полем используется VALIDATION_ERROR с описанием конкретного поля. Неизвестные поля входных DTO отклоняются с 400 VALIDATION_ERROR.

HTTP-статус и code выполняют разные задачи: статус задаёт общий класс результата, code различает причины внутри одного статуса. Например, занятость слота и закрытое время отмены дают 409, но разные коды причин.

## Таблица ошибок

| Ситуация | HTTP-статус | code | Объяснение |
|---|---|---|---|
| Тело запроса не является корректным JSON | 400 Bad Request | MALFORMED_JSON | Не удалось разобрать тело запроса |
| Отсутствует обязательное поле/параметр, неверен UUID, тип, значение, период, длительность или выравнивание слота; передано неизвестное поле DTO | 400 Bad Request | VALIDATION_ERROR | Некорректные данные запроса; подробности в fieldErrors |
| Нет приемлемой аутентификации | 401 Unauthorized | AUTHENTICATION_REQUIRED | Необходимо установить личность пользователя |
| Роль не разрешает операцию или пользователь не владелец существующей брони и не ADMIN | 403 Forbidden | FORBIDDEN | Недостаточно прав для выполнения операции |
| Корректный UUID комнаты не найден | 404 Not Found | ROOM_NOT_FOUND | Комната не найдена |
| Корректный UUID слота не найден | 404 Not Found | SLOT_NOT_FOUND | Слот не найден |
| Корректный UUID брони не найден | 404 Not Found | BOOKING_NOT_FOUND | Бронирование не найдено |
| У слота уже есть ACTIVE-бронь | 409 Conflict | SLOT_ALREADY_BOOKED | Слот уже забронирован |
| При создании брони начало слота уже наступило: startsAt не позже текущего времени | 409 Conflict | SLOT_ALREADY_STARTED | Слот уже начался; создать бронь нельзя |
| Попытка отменить ACTIVE-бронь, когда начало слота уже наступило | 409 Conflict | CANCELLATION_CLOSED | Время отмены активной брони истекло |
| Для комнаты уже существует слот с тем же моментом начала | 409 Conflict | SLOT_ALREADY_EXISTS | Слот этой комнаты с таким началом уже существует |
| Непредвиденный внутренний сбой | 500 Internal Server Error | INTERNAL_ERROR | Внутренняя ошибка сервиса |

Для ошибок отсутствия ресурса, доступа, конфликтов состояния и внутреннего сбоя fieldErrors пуст. Ответ 500 не содержит SQL, stack trace и внутренних сообщений драйвера.

Код выбирается по конкретной причине: конфликт частичного индекса bookings_one_active_per_slot_idx означает SLOT_ALREADY_BOOKED; конфликт уникальности пары комнаты и начала означает SLOT_ALREADY_EXISTS. Любую ошибку PostgreSQL, в том числе любую ошибку уникальности, нельзя автоматически превращать в занятость слота. Неожиданный конфликт идентификатора созданной сервером записи рассматривается как внутренняя ошибка.

## Правила доступа

Все операции требуют установленного сервером текущего пользователя. Отсутствующая или неприемлемая аутентификация даёт 401 AUTHENTICATION_REQUIRED. В будущей реализации ответ 401 сопровождается WWW-Authenticate, соответствующим выбранной схеме аутентификации; конкретная схема пока не реализована. Если личность установлена, но действие не разрешено, возвращается 403 FORBIDDEN.

| Операция | USER | ADMIN | Ограничение по владельцу |
|---|---|---|---|
| GET /api/v1/rooms | Разрешено | Разрешено | Не применяется |
| POST /api/v1/rooms | Запрещено | Разрешено | Не применяется |
| GET /api/v1/rooms/{roomId}/slots | Разрешено | Разрешено | Не применяется |
| POST /api/v1/rooms/{roomId}/slots | Запрещено | Разрешено | Не применяется |
| POST /api/v1/bookings | Разрешено | Разрешено | Бронь создаётся от имени текущего пользователя; userId не выбирается клиентом |
| GET /api/v1/bookings | Разрешено | Разрешено | Только история текущего пользователя, включая запросы ADMIN |
| GET /api/v1/bookings/{id} | Своя бронь | Любая бронь | Для USER требуется совпадение владельца с текущим пользователем |
| DELETE /api/v1/bookings/{id} | Своя бронь | Любая бронь | Правила статуса и времени отмены применяются также к ADMIN |

Роль и userId не принимаются как доказательство личности из тела запроса или произвольного клиентского заголовка. После подключения аутентификации текущего пользователя устанавливает сервер по проверенным данным. До этапа Security в первых локальных упражнениях допускается заранее выбранный сервером учебный пользователь и его роль из конфигурации/тестового сценария. Это учебный способ подстановки личности, а не реализованная аутентификация.

Проверка прав предшествует выполнению действия. Для существующей чужой брони USER получает 403, даже если бронь уже отменена. Неизвестный корректный UUID брони после проверки аутентификации даёт 404; неверный формат UUID относится к 400 VALIDATION_ERROR.

## Отмена и повторные запросы

DELETE /api/v1/bookings/{id} изменяет статус существующей записи на CANCELLED и сохраняет историю. Успешный ответ — 204 No Content без тела: JSON null и пустой объект не отправляются.

Правила обработки:

1. Установить текущего пользователя, проверить допустимую роль и формат id.
2. Найти бронь; при отсутствии вернуть 404 BOOKING_NOT_FOUND.
3. Проверить владельца или роль ADMIN; при отсутствии права вернуть 403 FORBIDDEN.
4. Если бронь уже CANCELLED, вернуть 204 без изменения данных. Это правило действует и после наступления начала слота.
5. Если бронь ACTIVE и startsAt не позже текущего времени, вернуть 409 CANCELLATION_CLOSED; статус сохраняется ACTIVE.
6. Если бронь ACTIVE и startsAt позже текущего времени, изменить статус на CANCELLED и вернуть 204.

| Состояние и условие | Результат | Состояние после запроса |
|---|---|---|
| Своя бронь или запрос ADMIN; ACTIVE; начало ещё не наступило | 204 No Content | Та же запись CANCELLED |
| Своя бронь или запрос ADMIN; CANCELLED; любое время | 204 No Content | Та же запись CANCELLED, без дополнительных изменений |
| Своя бронь или запрос ADMIN; ACTIVE; начало наступило | 409 CANCELLATION_CLOSED | Та же запись ACTIVE |
| Существующая чужая бронь; запрос USER | 403 FORBIDDEN | Запись не меняется |
| Бронь с корректным UUID не найдена; пользователь установлен | 404 BOOKING_NOT_FOUND | Запись не создаётся |

Проверка CANCELLED выполняется раньше ограничения времени отмены: уже успешная отмена остаётся успешной при повторе после начала слота. ADMIN также не может отменить ещё активную бронь после начала.

Повторный DELETE не создаёт новую запись, не меняет id/createdAt и не переводит CANCELLED обратно в ACTIVE. Поэтому повторение сохраняет эффект отмены. После отмены GET существующей брони возвращает 200 с тем же id, прежним createdAt и статусом CANCELLED; запись также остаётся в истории пользователя.

Повторное бронирование освобождённого слота — отдельный POST с новым UUID брони. Оно разрешено, если слот ещё не начался и активной брони нет. Прежняя CANCELLED-запись сохраняется; статус старой записи не восстанавливается.

Обычный POST не обещает распознавание повтора как той же операции. Если первая попытка сохранила бронь, а повтор пришёл при уже существующей ACTIVE, возвращается 409 SLOT_ALREADY_BOOKED. Предварительный GET доступности не гарантирует успеха POST. Поддержка Idempotency-Key не входит в первую версию.

# Примеры запросов и ответов

Это иллюстрации будущего контракта, а не результаты запросов к работающему сервису. В локальном учебном сценарии сервер заранее выбирает Anna с ролью USER и UUID 00000000-0000-0000-0000-000000000001. Подстановка пользователя выполняется на стороне сервера; клиент не передаёт userId или роль как доказательство личности. Способ передачи данных аутентификации будет определён при подключении Security.

Исходные комнаты и слот 7 взяты из учебного seed. Новая бронь с UUID 40000000-0000-0000-0000-000000000015 и временем создания 2026-10-27T12:00:00Z придумана для примера. Слот 7 принадлежит Sirius, начинается 2030-01-14T09:00:00Z и заканчивается 2030-01-14T10:00:00Z. В исходном наборе у него есть отменённая запись, но нет ACTIVE, поэтому он доступен до начала.

## 1. Запрос создания брони

Клиент передаёт только идентификатор слота; идентификатор новой брони, владельца, статус и время создания определяет сервер.

```http
POST /api/v1/bookings HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Accept: application/json

{"slotId":"00000000-0000-0000-0000-000000000007"}
```

## 2. Успешное создание — 201 Created

Location указывает на созданную бронь и совпадает с id в BookingResponse. Ответ содержит все восемь полей согласованного DTO.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/bookings/40000000-0000-0000-0000-000000000015

{
  "id": "40000000-0000-0000-0000-000000000015",
  "userId": "00000000-0000-0000-0000-000000000001",
  "slotId": "00000000-0000-0000-0000-000000000007",
  "roomId": "00000000-0000-0000-0000-000000000003",
  "status": "ACTIVE",
  "startsAt": "2030-01-14T09:00:00Z",
  "endsAt": "2030-01-14T10:00:00Z",
  "createdAt": "2026-10-27T12:00:00Z"
}
```

createdAt обозначает создание записи в октябре 2026 года; startsAt и endsAt — сам забронированный час в январе 2030 года.

## 3. Страница комнат — 200 OK

Нужны комнаты вместимостью не меньше восьми человек; запрашивается первая страница размером два элемента.

```http
GET /api/v1/rooms?minCapacity=8&page=0&size=2 HTTP/1.1
Host: localhost:8080
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "items": [
    {
      "id": "00000000-0000-0000-0000-000000000002",
      "name": "Vega",
      "capacity": 8,
      "hasProjector": false,
      "description": ""
    },
    {
      "id": "00000000-0000-0000-0000-000000000003",
      "name": "Sirius",
      "capacity": 8,
      "hasProjector": true,
      "description": "Near the window"
    }
  ],
  "page": 0,
  "size": 2,
  "totalElements": 3
}
```

Фильтру соответствуют Vega, Sirius и Luna, поэтому totalElements=3. На первой странице два элемента, упорядоченных по capacity ASC, id ASC; Luna попадёт на страницу page=1. Её description будет null, но поле останется в RoomResponse. Пустая строка описания Vega сохраняется как пустая строка.

## 4. Ошибка поля — 400 Bad Request

JSON корректен синтаксически, но строка abc не является UUID.

```http
POST /api/v1/bookings HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Accept: application/json

{"slotId":"abc"}
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "code": "VALIDATION_ERROR",
  "message": "Некорректные данные запроса",
  "fieldErrors": [
    {
      "field": "slotId",
      "message": "Ожидается UUID"
    }
  ]
}
```

Здесь применяется VALIDATION_ERROR, поскольку тело удалось разобрать. При сломанном синтаксисе JSON использовались бы MALFORMED_JSON и пустой fieldErrors.

## 5. Конфликт занятого слота — 409 Conflict

После успешного создания из примера 2 и до отмены из примера 6 клиент повторяет запрос из примера 1. У слота уже есть ACTIVE-бронь, поэтому новая запись не сохраняется.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "code": "SLOT_ALREADY_BOOKED",
  "message": "Слот уже забронирован",
  "fieldErrors": []
}
```

Формат slotId корректен; причина связана с состоянием слота, а не с ошибкой отдельного поля. Первая бронь остаётся ACTIVE, дополнительная запись не создаётся. Внутреннее имя индекса и текст SQL-ошибки клиенту не передаются.

## 6. Успешная отмена — 204 No Content

Anna отменяет созданную в примере 2 бронь до начала слота.

```http
DELETE /api/v1/bookings/40000000-0000-0000-0000-000000000015 HTTP/1.1
Host: localhost:8080
Accept: application/json
```

```http
HTTP/1.1 204 No Content

```

Тело ответа отсутствует. Та же запись сохраняется со статусом CANCELLED; id и createdAt не меняются. Повтор этого DELETE от владельца также возвращает 204 без тела, в том числе после наступления начала слота. Последующий GET этой брони возвращает 200 и тот же BookingResponse, в котором status равен CANCELLED.

# Связь контракта с базой данных

Ниже описано проектирование будущей обработки запросов на основе сохранённой SQL-схемы. Это описание операций и гарантий, а не код реализации или результат запуска API. Общие проверки аутентификации, ролей, формата полей и пагинации применяются ко всем соответствующим сценариям.

## 1. Поиск свободных слотов

**Цепочка:** roomId + период + availableOnly → проверка комнаты и параметров → выборка time_slots с связанным NOT EXISTS по ACTIVE при запросе доступных слотов → сортировка и страница SlotResponse → 200.

| Этап | Ответственность |
|---|---|
| Вход | roomId из пути; from, to, availableOnly, page и size из query parameters |
| Приложение | Проверяет UUID, существование комнаты, from < to, формат времени со смещением и параметры страницы; определяет момент проверки доступности |
| Выборка БД | Выбирает слоты комнаты с starts_at внутри [from, to). При availableOnly=true дополнительно требует starts_at позже момента проверки и NOT EXISTS связанной брони, у которой bookings.slot_id равен time_slots.id и status='ACTIVE' |
| Подготовка страницы | Применяет starts_at ASC, id ASC; считает totalElements с теми же фильтрами до ограничения страницы; получает данные текущей страницы |
| Защита БД | Внешний ключ time_slots.room_id поддерживает связь с комнатой. Чтение не резервирует слот; частичный уникальный индекс понадобится при создании брони |
| Ответ | 200 со страницей SlotResponse; для существующей комнаты без результатов items пуст; неизвестная комната — 404 ROOM_NOT_FOUND |

При availableOnly=false отбор по будущему времени и отсутствию ACTIVE не применяется: возвращаются все слоты комнаты в периоде. available вычисляется для каждого элемента по двум условиям доступности, включая будущий startsAt.

## 2. Создание брони

**Цепочка:** slotId → текущий пользователь и проверка будущего слота → INSERT в bookings со статусом ACTIVE → FK, CHECK и частичный уникальный индекс → 201 либо конкретная ошибка.

| Этап | Ответственность |
|---|---|
| Вход | slotId из CreateBookingRequest; пользователь установлен сервером |
| Приложение | Проверяет формат UUID, существование слота и starts_at позже текущего времени; предварительная проверка занятости может дать понятный ранний отказ, но не заменяет индекс |
| Изменение БД | Создаёт новую запись bookings с новым id, user_id текущего пользователя, указанным slot_id и статусом ACTIVE; created_at фиксируется при вставке. Изменение должно успешно зафиксироваться до ответа об успехе |
| Защита БД | PK обеспечивает уникальность id; FK проверяют ссылки на users и time_slots; NOT NULL и CHECK ограничивают обязательные поля и статусы; bookings_one_active_per_slot_idx допускает не более одной ACTIVE для slot_id |
| Ответ | После успешной фиксации — 201, BookingResponse и Location созданной брони; неизвестный слот — 404 SLOT_NOT_FOUND; начавшийся слот — 409 SLOT_ALREADY_STARTED; занятость — 409 SLOT_ALREADY_BOOKED |

Два запроса могут одновременно увидеть свободный слот. Индекс допускает сохранение только одной ACTIVE. При конфликте приложение распознаёт именно bookings_one_active_per_slot_idx и формирует SLOT_ALREADY_BOOKED. Поле roomId для ответа получается через связанный time_slots, а не добавляется в bookings.

## 3. История текущего пользователя

**Цепочка:** текущий пользователь + необязательный status → фильтр bookings.user_id → сортировка created_at DESC, id DESC → страница BookingResponse → 200.

| Этап | Ответственность |
|---|---|
| Вход | status, page и size из query parameters; userId установлен сервером |
| Приложение | Проверяет допустимость status и страницы; ограничивает историю текущим пользователем, включая обращения ADMIN |
| Выборка БД | Отбирает bookings по user_id; при наличии status добавляет этот фильтр. Через time_slots получает room_id, starts_at и ends_at для BookingResponse |
| Подготовка страницы | Сортирует по bookings.created_at DESC, bookings.id DESC; считает totalElements с тем же пользовательским и статусным фильтром; затем ограничивает страницу |
| Защита БД | FK сохраняют корректные связи брони. Принадлежность запрашиваемой истории пользователю обеспечивает приложение через обязательный фильтр, а не сам внешний ключ |
| Ответ | 200 со страницей BookingResponse; пустая история и страница за концом списка возвращают items=[] |

Без фильтра status история включает ACTIVE и CANCELLED. Индекс (user_id, created_at DESC, id DESC) — обоснованный кандидат для большой истории; его обсуждение в документации не означает, что он уже создан в основной таблице.

## 4. Отмена брони

**Цепочка:** id → существование и владелец/ADMIN → состояние и время → UPDATE status на CANCELLED → сохранение истории → 204 без тела.

| Этап | Ответственность |
|---|---|
| Вход | id брони из пути; текущий пользователь и роль установлены сервером |
| Приложение | Проверяет формат id, наличие записи и право владельца/ADMIN; затем статус и время. Для CANCELLED сразу применяется успешный повтор, даже после начала слота; для ACTIVE требуется starts_at позже текущего времени |
| Изменение БД | Для допустимой отмены обновляет status существующей bookings на CANCELLED; id, user_id, slot_id и created_at сохраняются. Проверки состояния и изменение координируются в транзакции; после успешной фиксации возвращается успех |
| Защита БД | CHECK допускает CANCELLED. После изменения запись перестаёт участвовать в частичном индексе ACTIVE, поэтому слот может получить новую активную бронь. БД сама не проверяет владельца или допустимое время отмены |
| Ответ | 204 без тела для успешной и повторной отмены; 404 BOOKING_NOT_FOUND при отсутствии; 403 FORBIDDEN без права; 409 CANCELLATION_CLOSED для ACTIVE после наступления начала |

Физического DELETE строки нет. Повтор не создаёт запись и не меняет время создания. Позднейшее бронирование освобождённого слота создаёт отдельную запись с новым UUID; оно разрешено только до начала слота и при отсутствии другой ACTIVE.

## 5. Создание слота

**Цепочка:** roomId + startsAt/endsAt → ADMIN, существующая комната, 60 минут и целый час UTC → INSERT в time_slots → FK, CHECK и UNIQUE(room_id, starts_at) → 201 либо конкретная ошибка.

| Этап | Ответственность |
|---|---|
| Вход | roomId из пути; startsAt и endsAt из CreateSlotRequest |
| Приложение | Проверяет роль ADMIN, формат roomId, существование комнаты, формат времени со смещением; после приведения к UTC начало приходится на целый час, конец — ровно через 60 минут |
| Изменение БД | Создаёт time_slots с новым id, room_id и моментами начала/конца; после успешной фиксации формирует SlotResponse |
| Защита БД | PK проверяет уникальность id; FK room_id ссылается на rooms; NOT NULL требует время и комнату; CHECK проверяют часовую длительность и выравнивание начала; UNIQUE(room_id, starts_at) запрещает дубликат начала для комнаты |
| Ответ | 201 с SlotResponse; неправильные поля/время — 400 VALIDATION_ERROR; отсутствие комнаты — 404 ROOM_NOT_FOUND; дубликат комнаты с началом — 409 SLOT_ALREADY_EXISTS; отсутствие роли — 403 FORBIDDEN |

Непересечение разных слотов одной комнаты обеспечивают три правила вместе: длительность 60 минут, начало в целый час UTC и уникальность (room_id, starts_at). Частичный индекс на bookings отвечает за другое правило — единственную ACTIVE на уже существующий слот.

## Граница проверок приложения и БД

| Проверка | Приложение | База данных |
|---|---|---|
| Формат JSON, названия полей и правила DTO | Разбирает и проверяет запрос, формирует 400 | Не получает HTTP/JSON-запрос напрямую |
| Текущий пользователь, роль и владение бронью | Устанавливает личность и проверяет права | FK не является проверкой личности или владельца запроса |
| Бронирование и отмена до начала слота | Проверяет время в рамках сценария | Динамическое условие с текущим временем не используется как постоянный CHECK |
| Существование связанных сущностей | Проверяет для понятного ответа | FK не позволяет сохранить неизвестную ссылку |
| Одна ACTIVE на слот | Может предварительно проверить | Частичный уникальный индекс гарантирует правило при конкурентных вставках |
| Длительность, выравнивание и уникальное начало слота комнаты | Проверяет для понятной ошибки | CHECK и UNIQUE сохраняют целостность данных |

Названия ограничений и индексов помогают приложению определить причину отказа. Конфликт bookings_one_active_per_slot_idx соответствует SLOT_ALREADY_BOOKED, конфликт пары (room_id, starts_at) — SLOT_ALREADY_EXISTS. Другие ошибки, включая неожиданный конфликт сгенерированного id, не превращаются автоматически в 409 занятого слота.

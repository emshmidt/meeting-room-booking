# Проверка десериализации JSON

Проверка выполнена 18 ноября 2026 года. Использовались отдельные запуски с `--app.demo-user=vera` для комнат и слотов и `--app.demo-user=anna` для бронирований. Успешный POST меняет состояние в памяти, поэтому сценарии создания повторяются на исходных данных или для свободного периода.

## Настройки

- [application.yaml](../src/main/resources/application.yaml) задаёт отказ при неизвестных полях, запрещает преобразование дробных чисел в целые и ограничивает преобразования скалярных типов.
- [JacksonConfig](../src/main/java/com/learning/booking/config/JacksonConfig.java) запрещает преобразование целых и дробных чисел и логических значений в строки.
- [CreateSlotRequest](../src/main/java/com/learning/booking/dto/CreateSlotRequest.java) проверяет оба поля времени через `OffsetDateTimeDeserializer`. Принимаются JSON-строки с явным смещением.
- [CreateBookingRequest](../src/main/java/com/learning/booking/dto/CreateBookingRequest.java) использует `StrictUuidDeserializer` для `slotId`. Допускается стандартная форма `8-4-4-4-12` с дефисами.

## Комнаты

| Запрос или входное значение | Фактический результат |
|---|---|
| Лишний `id` | `400`. |
| `capacity: 4.5`, `capacity: "4"`, `capacity: ""` | По `400` для каждого тела. |
| `hasProjector: "false"`, `hasProjector: 0` | По `400`. С JSON-значением `false` корректный запрос вернул `201`. |
| `name: 123`, `description: true` | До настройки получен `201` со строками `"123"` и `"true"` соответственно. После настройки оба запроса дали `400`. |
| `description` пропущено, передано как `null` или как `""` | Во всех случаях получен `201`. Пропуск и явный `null` дали `description: null`, пустая строка сохранилась как `""`. |
| GET после создания Atlas с `description: null` | `200`, `totalElements=5`. У Atlas и Orion описание `null`, у Vega — `""`. |

## Слоты

| Запрос или входное значение | Фактический результат |
|---|---|
| Числовые `startsAt` или `endsAt` | До настройки числовой `startsAt` создал слот с `201`, а числовой `endsAt` дошёл до проверки дубликата и дал `409`. После настройки оба тела дают `400` при десериализации. |
| Массив или строка без смещения в `startsAt` или `endsAt` | По `400` для каждого поля и каждой формы. |
| Слот Orion `18:00+03:00–19:00+03:00` | После настройки получен `201` с `15:00Z–16:00Z`. |
| Слот Orion `20:00+03:00–21:00+03:00` и последующий GET | POST вернул `201` с `17:00Z–18:00Z`. GET интервала `[17:00Z, 18:00Z)` вернул `200` и ту же запись, `totalElements=1`. |

Входные даты слотов в таблице относятся к 14 января 2030 года.

## Бронирования

| Вход или операция | Фактический результат |
|---|---|
| `slotId` равен `"abc"`, `""`, `"1-1-1-1-1"`, UUID в Base64 или UUID с пробелами по краям | По `400` для каждого тела. |
| `slotId` содержит корректный UUID отсутствующего слота | `404` с пустым телом. |
| `slotId` содержит корректный UUID свободного слота | `201`, создана бронь `ACTIVE`. Подтверждено на свежей сборке с исходными данными. |
| GET истории Anna на исходных данных | `200`, `totalElements=3`. Поля `createdAt`, `startsAt` и `endsAt` сериализованы с суффиксом `Z`. |

## Причины ошибок чтения

В обоих случаях Spring отклонил тело до вызова сервиса. Типы вложенных причин `HttpMessageNotReadableException` подтверждены в отладчике.

| Тело `POST /api/v1/bookings` | Полученный HTTP-статус | Вложенная причина | Код по контракту |
|---|---:|---|---|
| `{"slotId":` | 400 | `UnexpectedEndOfInputException` | `MALFORMED_JSON`, `fieldErrors=[]`. |
| `{"slotId":"abc"}` | 400 | `MismatchedInputException` | `VALIDATION_ERROR`, поле `slotId`. |

Столбец с кодами описывает [контракт ответа](api-contract.md#единый-формат-ошибки). В проверенной сборке оба ответа имели стандартное тело ошибки Spring.

Запросы для воспроизведения сохранены в [rooms.http](../requests/rooms.http), [slots.http](../requests/slots.http) и [bookings.http](../requests/bookings.http).

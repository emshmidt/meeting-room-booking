# Интеграция PostgreSQL

Цель — перенести хранение комнат, пользователей, слотов и броней в PostgreSQL. После миграции все восемь операций REST API должны проходить текущую приёмку, а созданные данные должны сохраняться при перезапуске приложения. [Контракт API](api-contract.md) · [Текущая HTTP-приёмка](api-verification.md)

## 1. Подключить PostgreSQL и Flyway

Перенести проверенную схему в версионированные миграции. Включить таблицы, внешние ключи, уникальность пары комнаты и времени начала слота и частичный уникальный индекс для активных броней. Предусмотреть воспроизводимую загрузку учебных данных.

- [ ] При запуске на пустой БД Flyway создаёт схему, а учебный набор содержит 4 комнаты, 3 пользователей, 8 слотов и 6 броней.
- [ ] После повторного запуска применённые миграции не запускаются снова. Учебные записи и данные, созданные через API, сохраняются без дубликатов.

## 2. Добавить JPA-сущности и репозитории

Описать отображение комнат, пользователей, слотов и броней на таблицы. Бронь связана с пользователем и слотом, слот — с комнатой. Подключить репозитории к существующим сервисам.

- [ ] После сохранения бронь читается из БД вместе с UUID владельца, UUID комнаты и временем начала и конца слота.
- [ ] Внешние ключи отклоняют запись со ссылкой на отсутствующего пользователя, слот или комнату.

## 3. Перенести чтение, фильтрацию и пагинацию в БД

Для комнат сохранить фильтр вместимости. Для слотов применить период `[from, to)` по времени начала, а для доступности проверить будущее начало и отсутствие `ACTIVE`-брони. Для истории сохранить фильтры по пользователю и статусу, сортировку `created_at DESC, id DESC` и подсчёт `totalElements` до ограничения страницы.

- [ ] В исходном наборе для Orion за период с `09:00Z` включительно до `11:00Z` исключительно, пока слоты ещё впереди, `availableOnly=true` оставляет слот на `10:00Z`.
- [ ] В исходной истории Anna при `page=0&size=2` приходят брони `…03`, затем `…02`. `totalElements=3` без фильтра и `totalElements=2` при `status=CANCELLED`.
- [ ] Страница за пределами выдачи возвращает `200` с `items=[]` и сохраняет общий счётчик подходящих записей.

## 4. Перенести создание и отмену в транзакции

Сохранять новую бронь со статусом `ACTIVE` и читать `createdAt` из значения `created_at`, которое записала БД. При отмене сначала проверять права. Если бронь уже имеет статус `CANCELLED`, вернуть `204` с пустым телом, даже если слот уже начался. Для `ACTIVE` проверить, что старт ещё впереди, затем изменить статус существующей записи на `CANCELLED`. Возвращать успешный HTTP-ответ после фиксации изменения.

- [ ] Два одновременных POST на один свободный будущий слот дают один `201 Created` и один `409 SLOT_ALREADY_BOOKED`. В БД остаётся ровно одна `ACTIVE`-бронь на этот слот.
- [ ] Нарушение уникальности пары комнаты и начала слота даёт `409 SLOT_ALREADY_EXISTS`. Конфликты различаются по ограничению, которое отклонило запись.
- [ ] Поле `createdAt` новой брони совпадает с прочитанным из БД значением в UTC. Первый DELETE до начала слота и повторный DELETE уже отменённой брони, в том числе после начала слота, дают `204` с пустым телом. GET возвращает `CANCELLED` с прежними `id` и `createdAt`.

## 5. Повторить HTTP-приёмку на PostgreSQL

Пройти все восемь операций по сохранённому отчёту, включая проверки владельца и администратора. Сверить ответы и описание в Swagger с контрактом.

- [ ] Успешные ответы, `Location`, пустое тело `204`, формат ошибок, фильтры и правила доступа совпадают с текущей приёмкой.
- [ ] Созданная бронь читается по тому же UUID после перезапуска приложения. Отменённая бронь после перезапуска сохраняет статус `CANCELLED`.
- [ ] В отчёте о проверке API зафиксированы результаты прогона с PostgreSQL.

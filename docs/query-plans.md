# Эксперимент с индексом на расширенном учебном наборе

## Версия и источник результатов

Сервер PostgreSQL: **18.6 (Postgres.app)**. Версия проверена 23 октября 2026 года командой `SHOW server_version` в базе `booking_training` на `localhost:5432`.

Планы ниже перенесены из сохранённых комментариев `sql/10-day-3-index-lab.sql`. Учебный скрипт при подготовке документа повторно не запускался; показатели относятся к зафиксированным выполнениям пользователя.

## Размер и устройство набора

- Временная таблица `day3_slots_lab`, доступная только в создавшем её соединении.
- Поля: `id uuid`, `room_id uuid NOT NULL`, `starts_at timestamptz NOT NULL`, `ends_at timestamptz NOT NULL`.
- **100 000 строк: 100 условных комнат × 1 000 слотов каждой комнаты.** Сохранённый результат наполнения: `INSERT 0 100000`.
- Для каждой комнаты слоты начинаются с `2030-01-01 00:00:00+00`, идут последовательно с шагом один час и длятся один час.
- Данные сформированы декартовым произведением двух `generate_series`. Общий номер слота: `(room_no - 1) * 1000 + slot_no`; номера преобразованы в UUID дополнением текстового представления слева нулями до 32 символов.
- До первого замера таблица не имела индексов, первичного ключа, уникальных ограничений или внешних ключей. Затем добавлен один неуникальный B-tree индекс.
- Перед обоими замерами выполнен `ANALYZE day3_slots_lab`; данные и условия отбора между замерами не менялись.
- Основная таблица `public.time_slots` и её ограничения в эксперименте не изменялись.

## Точный исследуемый запрос

В обоих случаях использован один запрос: слоты одной условной комнаты с началом в полуоткрытом диапазоне `[2030-01-14 09:00 UTC, 2030-01-14 11:00 UTC)`.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, room_id, starts_at, ends_at
FROM day3_slots_lab
WHERE room_id = '00000000-0000-0000-0000-000000000001'
  AND starts_at >= '2030-01-14 09:00:00+00'
  AND starts_at < '2030-01-14 11:00:00+00'
ORDER BY starts_at;
```

Ожидаемый и фактический результат — **2 строки**, слоты с началом в 09:00 и 10:00 UTC. В тексте планов границы показаны в UTC+3: 12:00–14:00; это тот же интервал.

## Созданный индекс

```sql
CREATE INDEX day3_slots_lab_room_start_idx
ON day3_slots_lab (room_id, starts_at);
```

B-tree используется по умолчанию. Индекс неуникальный: первым идёт `room_id`, вторым `starts_at`. Равенство по комнате ограничивает область поиска, затем применяется диапазон времени; такой порядок также соответствует сортировке начала слотов одной комнаты.

После создания индекса перед вторым замером обновлена статистика:

```sql
ANALYZE day3_slots_lab;
```

## Сравнение

| Показатель | До индекса | После индекса |
|---|---|---|
| Способ чтения | `Seq Scan` | `Index Scan` по `day3_slots_lab_room_start_idx` |
| Отдельная сортировка | `Sort`, quicksort, 25 kB | Нет отдельного узла `Sort` |
| Оценка выходных строк | 2 | 2 |
| Фактические выходные строки | 2 при `loops=1` | 2 при `loops=1` |
| Строки, отброшенные фильтром | 99 998 | Отдельный `Filter` не показан; условия находятся в `Index Cond` |
| Буферы выполнения | `local hit=935` | `local hit=1 read=3` |
| Полная стоимость верхнего узла, условные единицы | 2685.02 | 10.21 |
| Planning Time | 0.701 ms | 0.475 ms |
| Execution Time | 14.890 ms | 0.087 ms |

До индекса PostgreSQL последовательно прочитал таблицу, отфильтровал 99 998 строк и отдельно отсортировал две подходящие. После индекса поиск выполнен по комнате и диапазону начала; отдельная сортировка исчезла. Результат остался тем же, а время выполнения в сохранённом опыте снизилось с 14.890 до 0.087 мс.

В обоих планах оценка количества выходных строк совпала с фактом: **2**. Числа `0.701 ms` и `0.475 ms` — время планирования, а не оценки числа строк. Подписи `(12 rows)` и `(8 rows)` означают количество строк текста планов, а не число найденных слотов.

Буферы `local` относятся к временной таблице и её индексу. Показатели буферов родительского узла включают обращения дочернего узла: два упоминания `local hit=935` в первом плане не нужно складывать. Отдельный раздел `Planning` описывает обращения при планировании, а не при выполнении запроса. `read` означает чтение блока в буфер PostgreSQL, но сам по себе не доказывает физическое чтение с диска: данные могли находиться в кеше ОС.

## Ограничения замера

- Сохранено по одному выполнению до и после. Кеши, текущая нагрузка и накладные расходы измерения могут влиять на время; это учебное наблюдение, а не гарантия постоянного ускорения.
- После создания индекса повторён `ANALYZE`; оценки планировщика могут зависеть от собранной статистики.
- Данные равномерные и синтетические, таблица временная, отбор очень узкий — 2 строки из 100 000. Результат нельзя автоматически переносить на другие запросы, рабочую нагрузку или обычную постоянную таблицу.
- Время создания индекса, его фактический размер и замедление записей здесь не измерялись. Эти затраты не входят в приведённое `Execution Time` исследуемого `SELECT`.
- Подходящий индекс не обязывает планировщик выбирать индексное чтение для любого запроса: на маленьком наборе или при широком отборе последовательное чтение может оказаться выгоднее.

## Цена дополнительного индекса

Индекс занимает дополнительное место для ключей и служебной структуры. В этом опыте он временный и существует вместе с таблицей в рамках соединения; точный размер не сохранён и здесь не оценивается числом.

Добавление строк и изменение индексируемых значений требуют обслуживания индекса; удаление и последующая очистка также создают дополнительную работу. Создание самого индекса требует времени и ресурсов, поэтому решение оценивают с учётом частоты запросов и записей. Ускорение узкого `SELECT` не означает бесплатного ускорения всей работы с таблицей.

Для истории Anna сохранён отдельный план `Seq Scan → Sort`: он возвращает **3 брони**, отбрасывая 3 другие строки. Предложенный индекс `(user_id, created_at DESC, id DESC)` остаётся кандидатом для большой истории; в данном эксперименте он не создавался и его эффект не измерялся.

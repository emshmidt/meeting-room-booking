# Meeting Room Booking API

Проект REST API для бронирования переговорных комнат с часовыми слотами. Контракт предусматривает поиск свободных слотов, создание и отмену броней с сохранением истории, а также добавление комнат и слотов администраторами.

На Spring Boot с Spring Web MVC и Validation реализованы восемь операций API. Пользователи могут просматривать комнаты, искать слоты, создавать и читать брони, смотреть свою историю и отменять бронирования. Администраторы также создают комнаты и часовые слоты. Контракт доступен через OpenAPI и Swagger UI. Приложение хранит данные в памяти и при каждом запуске загружает исходный набор.

## Что добавлено

- Доменная модель: `Room`, `User`, `TimeSlot`, `Booking`, роли `USER`/`ADMIN` и статусы `ACTIVE`/`CANCELLED`.
- In-memory репозитории с синхронизированным доступом, проверкой повторных UUID и возвратом неизменяемых снимков данных.
- `DemoDataInitializer` с фиксированным набором из 4 комнат, 3 пользователей, 8 слотов и 6 броней.
- Профиль `memory` для API и обычных тестов. Профиль `postgres` настраивает JDBC и Flyway для отдельной проверки подключения и миграций.
- UTC `Clock` и `CurrentUserProvider` с выбором демонстрационного пользователя через конфигурацию сервера.
- `RoomController`, `RoomService`, `RoomResponse` и `PageResponse<T>`: GET комнат с фильтром вместимости, сортировкой, пагинацией и отклонением неверных параметров с HTTP 400.
- `CreateRoomRequest` и POST комнат: роль ADMIN, проверки полей до сохранения, серверный UUID и ответ 201; предметные ошибки отдельно переводятся в 400/403.
- `SlotController`, `SlotService`, `CreateSlotRequest` и `SlotResponse`: создание часовых слотов ADMIN с проверкой дубликатов, поиск по периоду и доступности, сортировка и пагинация.
- `BookingController`, `BookingService`, `CreateBookingRequest` и `BookingResponse` поддерживают создание ACTIVE-брони будущего свободного слота с ответом 201 и Location. `BookingServiceTest` проверяет конфликт повторного запроса и сохранность первой записи.
- `GET /api/v1/bookings/{id}` доступен владельцу или ADMIN. `GET /api/v1/bookings` возвращает собственную историю, а `DELETE /api/v1/bookings/{id}` отменяет бронь с сохранением записи.
- Unit-тест `RoomServiceTest`, проверяющий фильтр, оба ключа сортировки, страницы, общий счётчик и большое смещение.

Для первой сборки нужен доступ к репозиторию зависимостей. Выполняйте команды из корня репозитория.

### Команды

Проверьте, что Wrapper использует JDK 21, соберите проект и запустите JAR от Anna.

```bash
./mvnw -v
./mvnw clean verify
java -jar target/meeting-room-booking-0.0.1-SNAPSHOT.jar --app.demo-user=anna
```

Для запуска из исходников можно использовать `./mvnw spring-boot:run`. Перед новым запуском остановите предыдущий процесс через Ctrl+C, чтобы освободить порт `8080`.

### Конфигурация и HTTP-проверка

Сервер выбирает демонстрационного пользователя один раз при запуске. Подставьте в команду `--app.demo-user=boris` для другого пользователя с ролью USER или `--app.demo-user=vera` для ADMIN. По умолчанию используется Anna. В профиле `memory`, который используется по умолчанию, перезапуск сбрасывает изменения и восстанавливает исходный набор. HTTP-аутентификация запланирована.

В другом терминале запросите первую страницу комнат вместимостью от 8 человек.

```bash
curl -i 'http://localhost:8080/api/v1/rooms?minCapacity=8&size=2'
```

Ожидаемый ответ — `200 OK`, в `items` идут Vega и Sirius, `totalElements=3`.

Откройте [Swagger UI](http://localhost:8080/swagger-ui/index.html) или [спецификацию OpenAPI](http://localhost:8080/v3/api-docs). Для короткой проверки от Anna найдите свободный будущий слот через `GET /api/v1/rooms/{roomId}/slots` с `availableOnly=true`, передайте его UUID в `POST /api/v1/bookings` и выполните GET по `Location` из ответа `201 Created`. Пример параметров поиска и весь порядок запросов есть в [отчёте о проверке API](docs/api-verification.md).

### Как проходит запрос бронирования

Spring MVC читает JSON и валидирует `CreateBookingRequest`. `BookingController` передаёт запрос в `BookingService`, который проверяет слот и сохраняет бронь через `BookingRepository`. Контроллер возвращает `BookingResponse` со статусом `201` и заголовком `Location`. `ApiExceptionHandler` формирует JSON-ответ при ошибке.

## Границы первой версии

- Слот длится 60 минут и начинается в целый час UTC; интервал считается полуоткрытым: `[start, end)`.
- Пара `(room_id, starts_at)` уникальна. Вместе с длительностью и выравниванием это исключает пересечения слотов одной комнаты.
- У слота может быть не более одной ACTIVE-брони; CANCELLED-записи сохраняются в истории. Правило ACTIVE обеспечивает частичный уникальный индекс `bookings_one_active_per_slot_idx`.
- Бронирование и отмена активной брони разрешены до начала слота. Отменять может владелец или ADMIN; повтор уже успешной отмены не изменяет данные.
- Полный набор HTTP-операций, DTO и ролей описан в контракте. В памяти реализованы восемь маршрутов — GET/POST комнат, GET/POST слотов, создание брони, чтение одной брони, собственная история и отмена. Создание и отмена защищены монитором BookingService в пределах процесса. Частичный уникальный индекс относится к SQL-схеме. Перенос хранения REST API в PostgreSQL описан в [плане интеграции](docs/postgresql-integration-backlog.md).

## Восстановление исходного набора

Последовательность предназначена для **новой пустой проверочной БД**. Перед запуском проверить имя текущей БД; существующую рабочую БД очищать не требуется. SQL-файлы можно открывать в клиенте или выполнять их содержимое в подключённой к нужной БД SQL-консоли.

1. Создать `booking_training_day5_check` и подключиться к ней. Если она уже содержит таблицы после проверки, установочные файлы повторно целиком не запускать; для нового восстановления выбрать другую пустую БД.
2. Выполнить [01-schema.sql](sql/01-schema.sql), затем [02-seed.sql](sql/02-seed.sql). На этом этапе создано пять комнат.
3. Из [03-queries.sql](sql/03-queries.sql) выполнить только удаление временной комнаты с UUID `00000000-0000-0000-0000-000000000005`. Должны остаться четыре комнаты.
4. Выполнить [04-day-2-schema.sql](sql/04-day-2-schema.sql), затем [05-day-2-seed.sql](sql/05-day-2-seed.sql).
5. В [14-day-4-active-booking-index.sql](sql/14-day-4-active-booking-index.sql) проверить отсутствие нескольких ACTIVE на слот и существующие индексы. При отсутствии нужного индекса выполнить блок его создания; затем проверить определение через `pg_indexes`.
6. Сверить количества строк, свободные слоты, отчёт комнат и историю Anna с результатами ниже.

Файлы 7, 10, 11 и 13 относятся к экспериментам и не входят в эту установочную последовательность. Обычные контрольные запросы можно выполнять отдельными блоками из файлов 6, 8 и 9. Основные таблицы находятся в `public`; `day4_lab` содержит отдельные таблицы для опытов с транзакциями и гонкой. Их строки не входят в количества исходного набора.

# Meeting Room Booking API

Учебный проект сервиса бронирования переговорных комнат с часовыми слотами. Пользователь находит свободный слот, создаёт бронь, просматривает свою историю и отменяет бронь с сохранением записи. Администратор создаёт комнаты и слоты.

Подготовлены SQL-схема, учебные данные, эксперименты PostgreSQL и контракт API. Добавлен каркас Spring Boot с Spring Web MVC и Validation. Сейчас приложение запускает встроенный HTTP-сервер; контроллеры и бизнес-сценарии бронирования ещё предстоит реализовать.

### Команды

Все команды ниже выполняются из корня проекта — локально это `/Users/emiliashmidt/IdeaProjects/booking-training`. Имя Maven-артефакта и репозитория GitHub — `meeting-room-booking`; совпадение имени локальной папки с ними не требуется.

Проверка среды, тестирование и сборка:

```bash
./mvnw -v
./mvnw test
./mvnw package
```

Запуск через Maven:

```bash
./mvnw spring-boot:run
```

Альтернативный запуск собранного приложения:

```bash
java -jar target/meeting-room-booking-0.0.1-SNAPSHOT.jar
```

Перед переключением способа запуска остановить предыдущий процесс через Ctrl+C, чтобы освободить порт. После изменения исходников перед запуском JAR повторить сборку. Файл с окончанием `.jar.original` не является исполняемым Boot JAR для этой команды.

### Конфигурация и HTTP-проверка каркаса

Настройки находятся в `src/main/resources/application.yaml`:

- `spring.application.name=meeting-room-booking` — имя приложения;
- `server.port=8080` — порт HTTP-сервера;
- `app.demo-user=anna` — подготовленное учебное свойство. Компонент, который будет читать его и выбирать пользователя, ещё не реализован; это не аутентификация.

Адрес локального сервера: `http://localhost:8080`.

Пока приложение запущено, открыть вторую вкладку терминала и выполнить:

```bash
curl -i http://localhost:8080/api/v1/rooms
```

На текущем каркасе фактически получен HTTP 404 при обоих способах запуска: контроллер `/api/v1/rooms` ещё отсутствует. Такой ответ подтверждает доступность HTTP-сервера, но не готовность операции списка комнат. После реализации контроллера этот запрос должен возвращать 200 со страницей комнат по контракту.

## Границы первой версии

- Слот длится 60 минут и начинается в целый час UTC; интервал считается полуоткрытым: `[start, end)`.
- Пара `(room_id, starts_at)` уникальна. Вместе с длительностью и выравниванием это исключает пересечения слотов одной комнаты.
- У слота может быть не более одной ACTIVE-брони; CANCELLED-записи сохраняются в истории. Правило ACTIVE обеспечивает частичный уникальный индекс `bookings_one_active_per_slot_idx`.
- Бронирование и отмена активной брони разрешены до начала слота. Отменять может владелец или ADMIN; повтор уже успешной отмены не изменяет данные.
- Доступ через HTTP, DTO и роли описаны в контракте. Работающий Spring API, подключение Java к БД, миграции и аутентификация пока не реализованы.

## Восстановление исходного набора

Последовательность предназначена для **новой пустой проверочной БД**. Перед запуском проверить имя текущей БД; существующую рабочую БД очищать не требуется. SQL-файлы можно открывать в клиенте или выполнять их содержимое в подключённой к нужной БД SQL-консоли.

1. Создать `booking_training_day5_check` и подключиться к ней. Если она уже содержит таблицы после проверки, установочные файлы повторно целиком не запускать; для нового восстановления выбрать другую пустую БД.
2. Выполнить [01-schema.sql](sql/01-schema.sql), затем [02-seed.sql](sql/02-seed.sql). На этом этапе создано пять комнат.
3. Из [03-queries.sql](sql/03-queries.sql) выполнить только удаление временной комнаты с UUID `00000000-0000-0000-0000-000000000005`. Должны остаться четыре комнаты.
4. Выполнить [04-day-2-schema.sql](sql/04-day-2-schema.sql), затем [05-day-2-seed.sql](sql/05-day-2-seed.sql).
5. В [14-day-4-active-booking-index.sql](sql/14-day-4-active-booking-index.sql) проверить отсутствие нескольких ACTIVE на слот и существующие индексы. При отсутствии нужного индекса выполнить блок его создания; затем проверить определение через `pg_indexes`.
6. Сверить количества строк, свободные слоты, отчёт комнат и историю Anna с результатами ниже.

Файлы 7, 10, 11 и 13 относятся к экспериментам и не входят в эту установочную последовательность. Обычные контрольные запросы можно выполнять отдельными блоками из файлов 6, 8 и 9. Основные таблицы находятся в `public`; `day4_lab` содержит отдельные таблицы для опытов с транзакциями и гонкой. Их строки не входят в количества исходного набора.
